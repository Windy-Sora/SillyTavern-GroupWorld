# 排查工作流与证据边界

## 1. 确定正在回答什么

“为什么大家都说话”可以先核对模式和人数约束；“昨天为什么小明不说话”需要那次运行的证据。用户只想调人数，不必读取所有聊天正文。不要为已明确的“整体看看导演”重新给任务分类菜单。

通过实际工具目录确定工具及资料来源。匿名运行概况可用 `muyu.director.inspect`，来源为 `directorDiagnostics`；当前参数按配置目录读取，来源通常为 `configSettings`。公开说明可按目录读取 director.modes、director.scoring、director.history。目录和合同是方法说明，不是当前值。

具体角色的历史原因需要相关历史、身份、消息或评分证据。先查 Provider 资料目录并使用实际返回的 sourceId、selector、revision；不要编造历史读取入口。拒绝后停止读取该资料，不换 Provider 绕行。有效授权不重复申请。

## 2. 当前模式与人数

- 公式模式使用公式选人规则和 `topN`；LLM 模式使用 `llmMaxSpeakers`。先读实际模式，再解释相关参数，不混用两种人数设置。
- `llmMaxSpeakers` 是实际发言人数的上限，不是候选池大小，也不要求每次选满。选人数与启用成员数相等，不证明没有筛选；当前上限也不证明历史上限。
- 仅有“成员3人、上限3人、最近记录选3人”时，只能说这次人数在允许范围内。不得据此说“上限开满导致吵闹”“不是筛选坏了”“模型多选没有代价”，也不能把连续多次全选当作筛选失效的证明。合理的全员参与、Prompt影响、模型选择和其他生成路径仍需对应证据；先报告原因未知，再按用户目标提出收紧上限的建议。建议有效不等于已经找到故障原因，不用后面的免责声明抵消前面的因果断言。
- 公式权重、触发器和主动性参数是否影响某条路径，要查具体字段合同及运行说明。不能只凭字段名宣布整个评分系统“没生效”。主动性基础分不等于角色当前主动性值。
- 模式关闭、非群聊、没有可用成员是当前可核对的阻断条件。接管失败标志只描述读取时的状态，不证明所有历史失败原因。

不得把仅有的匿名人数概况转成“最可能原因”或“最合理解释”的概率排序，再补一句“不是已证实”掩饰。缺少实际选人原因／Prompt／正文等证据时，原因未知；配置满足上限只能作为一致性观察，或按用户目标提出节奏调整选项。

人数记录也不是消息生成回执：“最近记录选3人”不能改写成“3个人已经一起开口”“吵闹的直接来源就是全员发言”。不知道实际是否发言、输出长短与用户所指吵闹现象时，就不能确定直接原因。建议降低人数上限只针对以后允许的选人数，不证明这次噪声来源或其他路径已经被核实。

## 3. 匿名状态能说明多少

`muyu.director.inspect` 不提供角色名、逐角色评分、reason 正文、消息正文、Prompt 或密钥。启用成员数不是白名单姓名列表。历史条数、最后一次人数及 reason 字段存在，只是结构信息，不证明那次生成成功、持久化成功或原因正确。

`lastChatLength` 是最后一份历史记录的消息长度锚点，不是当前聊天长度。不要用它和最近消息窗口比较，就声称模型看到了整段聊天。当前窗口设置也不能证明历史请求实际携带了多少内容。

历史可编辑、清空，也可能随消息修剪；swipe／regenerate 可能复用已有选择或走不同分支，不能假定每次都重新选人。没有评分或历史正文时，直接说明无法判断具体角色落选原因，而不是补一段心理分析。

## 4. 给建议或修改

先给与目标相关的少量发现。人数多不一定是故障，人数少也不一定是失败；确认用户想要的节奏后再提出参数建议，不默认所有用户都要 Top-1。

明确要求修改时查询字段合同、读取必要基线、提交仅包含点名字段的预览。不能顺手切模式、补开开关、清历史或实际启动发言。配置草稿、执行回执和持久化确认分开；失败、部分完成或 outcome_unknown 不自动重试。
