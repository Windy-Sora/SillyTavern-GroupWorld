# 多模块配置方案

纯设计仍可读取公共技能参考，不等于读取当前聊天。已有变量规则和业务事件可自动更新；脚本／自定义Agent不是唯一自动运行层，也不是所有系统的必需项。Provider作为只读视图是设计建议，不是JavaScript沙箱保证；删占位符不会停用完整渲染中的Provider。

涉及实际跨来源核对或多种操作落地时，先发布有界方案并按workflow关联实际读值及候选。纯文字设计、解释或简单单项预览不强制规划。关联不增加权限，也不判步骤完成。

先完整读取 references/workflow.md。已有专用技能可配合使用：整体配置检查处理只读核对，金币技能处理数值系统，Provider 技能处理代码资产；不要把它们重复加载成常驻全部指令。

用户要求商店、背包、任务进度、无限流等复杂系统实现时，完整读取 references/system-design.md，区分状态存储、Provider视图、DSL展示和实际更新；需要具体模板再加载DSL技能。简单单项修改不要求读取整套设计资料。

把用户目标转成最小可用方案，不为复杂请求反复询问“你要哪类任务”。只有会实质改变方案的缺失信息才澄清，例如余额是大家共用还是每个角色独立。可逆默认选择应作为提案说明，不假装用户已经确认。

先查工具及可编辑目录，按需要整理一份只读来源清单，再查询合同、读基线、核对依赖。读取批准不是写入批准，任务方案不是可执行的完整系统。

符合整单边界的变更可生成一份精确整单草稿；划分前查字段合同的 bundle.supported，不凭领域名拆单。超出边界的资产使用专用工具分阶段处理。不要承诺跨所有模块原子执行，也不要把只读合同查询或分析标成待写入步骤。

展示 GUI 名称、实际差异、全局／当前聊天范围、额外调用和数据风险。用户只要求方案或预览时不执行；明确执行请求下也尊重实际权限、工具边界与未知结果停止规则。
