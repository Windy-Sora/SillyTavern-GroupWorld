# 复杂系统：状态、视图与执行分工

## 从目标到最小结构

| 需求 | 优先组件 | 不应混淆 |
| --- | --- | --- |
| 余额、生命值、任务状态、背包 | 当前聊天变量及类型／作用域／更新规则 | Provider返回值不是持久状态 |
| 固定规则、商品目录、输出指引 | 自定义提示词content／dataJson；世界书按实际需要 | 保存不等于自动注入 |
| 动态来源或确定性派生视图 | 已有Provider；确需新代码才写用户Provider | render不是扣款入口 |
| 选择字段、过滤和列表展示 | DSL路径查询与循环 | DSL不计算总价、不赋值、不执行JS |
| 模型判定剧情事件与导演选人 | 现有功能Prompt与真实更新通道 | Prompt要求不保证正确执行 |
| 确定性动作或额外模型处理 | 明确需要时用脚本／自定义Agent | 启用不证明已运行，可能增加费用和副作用 |

先按已有专用技能核对合同，只载本任务需要的参考。用户只讨论设计时可用假设样本，不要求授权全部聊天；实际落地才读必要现状与基线。不能为了系统复杂度默认追加Agent或自动化。

这里的Provider“视图／不扣款”是设计约束，不是宿主强制的只读沙箱：用户Provider的render是任意JavaScript，可能有副作用。完整renderPrompt会执行所有未禁用的注册Provider，即使正文没有引用其占位符，不能通过删引用来保证不运行。各递归轮复用本次结果，不逐轮重新执行。需要精确模板或运行边界时加载DSL技能的syntax与runtime参考。

自动状态更新可复用已有变量更新规则和业务事件通道，不必为所有变化新增脚本。读取授权、草稿批准与实际自动更新是不同契约；不要声称每次游戏内变量更新都必须用户点击批准，也不要声称整单跨存储域原子生效。

## 金币与商店

共享余额可用当前聊天number变量party_gold；已有余额不能重置。收支规则区分delta增减和replace最终余额，无明确收支证据不更新。`{{?globalVars:party_gold.value}}` 读取余额，前提是同聊天确有该变量；回退文本“未提供”比0更适合缺证据时展示。

固定商品信息可用自定义提示词dataJson，如 `{ "stock": [{"id":"heal","name":"药水","price":5}] }`；名字shop_rules仅示例，不是内置项。`{{?shop_rules:stock[id=heal].price}}`可取5，但不能写 `{{?shop_rules:price*count}}` 计算总价。需要批量列表时增加ID列表和索引映射供循环，或读取现有结构后设计相容视图，不擅自迁移旧数据。

一次购买若需同时扣余额和加背包，当前工具的多个变量写入不是通用原子交易。不要把两个成功草稿称为事务；相关写入结果未知后停止，不重试扣款。用户要求严格防重复交易时需专门确定性实现及验证，不能用模型承诺百分百记账。金币只需余额计数时不扩成商店、背包和新Provider。

## 背包与任务进度

array适合简单ID列表，object适合物品数量映射；存储值的append／merge／delta和类型限制以变量编辑合同为准，merge不是自动数量加法。共享和逐角色由变量scope决定，不以姓名拼进共享ID假装逐角色。角色名、头像身份和工具character:N选择器各有用途，不能互代。

任务ID、进度和奖励规则可由明确变量／静态规则描述；剧情蓝图负责节点结构与推进。蓝图受保护完成信号及结构修改走专用通道，不让普通变量或脚本绕过保护。不要把已有进度替换成样本，也不要用新状态与旧状态双写而不定义权威来源。

## 无限流配置的可核对阶段

先提出最小世界规则、共享／逐角色状态及蓝图结构；明确复用或独立目标，保留未要求的旧资产。将实际操作映射到现有变量、普通全局参数、蓝图、Prompt、资源或代码专用工具。整单能否合并取决于实时bundle合同，不承诺全模块一次原子执行；不同存储域的结果独立汇报。

验证分开看：状态定义是否保存、当前值是否核对、模板是否实际渲染、自动更新是否在真实事件触发、模型行为是否符合规则。示例期望／静态格式／合成Worker测试只证明各自层面；不能用一层通过覆盖另外几层。优先给用户可用的最小系统，而不是一张全部开关开启的配置档。
